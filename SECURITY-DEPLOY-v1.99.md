# Ден и Нощ — безопасно въвеждане на промените (28.10.2026)

## Статус
Промените са само в GitHub клон `improvements-memorial-security-2026-10-28`.
`main`, Supabase и работещият сайт не се променят автоматично.
Няма 2FA. Входът остава с имейл и парола, но администраторските права се проверяват **на сървъра**.

## Какво е новото
- Публичен калкулатор: 3, 9, **20**, 40 дни; **3**, 6, 9 месеца; 1 година; отделни ICS и един общ ICS.
- Книжка: бутон **„Автоматично попълни за 1 година“**, който смята Задушниците през първата година след смъртта и добавя до 6, без да заменя ръчно въведените. Съществуващите функции за PDF, A6 книжка, Canon G2416, ред на страниците и ръчния печат не са променяни.
- Статистика: правилно броене на /kontakti/ и /kontakti.html; глобален лимит до 300 анонимни събития на минута, без IP/потребителски идентификатор.
- Права: отделен списък с позволени акаунти; ограничаване на аналитичните RPC и write операции върху продукти, категории, настройки и снимки.

## ЗАДЪЛЖИТЕЛНО: последователност на пускане
1. Запазете **backup на сайта и на Supabase базата**. Не изтривайте налични данни.
2. Първо проверете броя Auth потребители в Supabase: Authentication → Users.
3. Ако има точно **един реален администратор**: в SQL Editor изпълнете целия `supabase-security-and-analytics-v1.99.sql` преди качване на новия админ.
4. Ако има **повече от един** Auth акаунт: SQL нарочно отказва изпълнението и не прави частична промяна (BEGIN/COMMIT).
   Изберете правилния администратор от Authentication → Users и създайте разрешения запис в `public.agency_admins` по-долу, след което изпълнете миграцията отново. **Не добавяйте всички потребители.**
5. Проверете `agency_admins` (само позволени лица) и RLS политиките. Миграцията отказва да активира RLS на таблица, която още е без RLS, за да не прекъсне работа на сайта. Ако това се случи, политиките трябва да се прегледат ръчно, **преди** миграцията.
6. Едва след успешен SQL и регресионните тестове публикувайте файловете от клона. Първо пробвайте в отделно тестово копие; не замествайте продукционните файлове едновременно без възможност за rollback.
7. Проверете вход/изход, показване и редакция на продукт, качване/триене на продуктова снимка, статистика, /kontakti/ KPI, публичен каталог, книжка (PDF и Canon G2416) и некролози на A4.

## При повече от един Auth потребител
Първият опит за миграция ще върне грешка и ще се върне назад. След нея, преди повторен опит, в SQL Editor въведете **истинския имейл на текущия администратор**:

```sql
-- Ако миграцията е отказала, изпълнете първо това:
CREATE TABLE IF NOT EXISTS public.agency_admins (
  user_id uuid PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  created_at timestamptz NOT NULL DEFAULT now()
);
ALTER TABLE public.agency_admins ENABLE ROW LEVEL SECURITY;
REVOKE ALL ON public.agency_admins FROM anon, authenticated;

INSERT INTO public.agency_admins(user_id)
SELECT id FROM auth.users
WHERE lower(email)=lower('CHANGE_TO_REAL_ADMIN_EMAIL');
-- Проверете, че точно 1 ред е добавен и ID съвпада с Authentication → Users:
SELECT user_id FROM public.agency_admins;
```

Ако SELECT не върне ред, спрете и поправете имейла. След това изпълнете цялата миграция.

## Важни ограничения
- Лимитът за анонимна статистика е **глобален** (300 събития/мин), без IP tracking. Той ограничава масовото завишаване, но **не може да докаже, че кликовете са реални хора**. По-силна мрежова защита трябва да се настройва отделно на хостинга/edge ниво.
- GitHub няма пряк достъп до действителните Supabase настройки/данни. Скриптът добавя ограничителни `RESTRICTIVE` RLS политики към **write** действия и запазва вече съществуващите публични `SELECT` политики. За пълен одит трябва да се видят действащите RLS политики и grants в Supabase.
- Не съхранявайте лични данни за покойниците в статистиката. Некролозите и книжката остават обработвани локално в браузъра.
- Никакво автоматично мержване или качване към живия сайт не се прави от тази промяна.
